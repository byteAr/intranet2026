1. Descripción del Sistema

La plataforma Intranet Institucional es un sistema web de uso interno desarrollado para el Instituto Universitario GNA. Integra los siguientes módulos funcionales:

  • Chat institucional con mensajería en tiempo real y adjuntos
  • Gestión de incidencias con seguimiento de estado y asignación
  • Sistema de reservas de espacios y equipamiento
  • Módulo de correo con integración IMAP/SMTP al servidor de correo institucional
  • Redacción MTO (Draft-Mail) con flujo de aprobación y firma digital
  • Panel de administración con gestión de usuarios en Active Directory y Google Workspace
  • Notificaciones push y presencia en tiempo real (Socket.IO)

3. Autenticación y Gestión de Sesiones

3.1 Autenticación contra Active Directory

Todos los usuarios del sistema se autentican exclusivamente contra el Active Directory institucional mediante el protocolo LDAP. No existen contraseñas locales almacenadas en la base de datos del sistema. El servidor AD reside en la red interna y no es accesible desde internet.

  • Protocolo: LDAP sobre red interna (dominio iugnad.lan)
  • Credenciales de servicio: almacenadas como Docker Secret (no en variables de entorno planas)
  • Error de AD 773 (contraseña expirada) devuelve mensaje claro al usuario en lugar de error genérico
  • Los roles y permisos se extraen del atributo memberOf del AD en cada login

3.2 Tokens JWT con cookie httpOnly

Tras una autenticación exitosa, el servidor emite un token JWT que se entrega al navegador exclusivamente mediante una cookie httpOnly. Esta modalidad impide que cualquier script JavaScript (incluyendo eventuales scripts inyectados por ataques XSS) pueda leer o robar el token de sesión.

  • httpOnly: true — inaccesible desde JavaScript
  • SameSite: Strict — protección contra ataques CSRF
  • Secure: true en producción — solo transmitida por HTTPS
  • Vigencia del token: 8 horas
  • El payload incluye un identificador único de token (jti) generado criptográficamente
Mejora respecto a la versión anterior: En versiones previas el token JWT se almacenaba en localStorage del navegador, siendo accesible desde JavaScript. Esta vulnerabilidad fue corregida migrando a cookie httpOnly, eliminando el riesgo de robo de sesión por XSS.

3.3 Lista negra de tokens (Redis)

Al cerrar sesión, el identificador único del token (jti) se registra en Redis como token invalidado. Cualquier intento posterior de usar ese token es rechazado, incluso si el token aún no expiró. Esto garantiza que el logout sea efectivo e inmediato.

  • Almacenamiento: Redis 7 en memoria, accesible solo desde la red interna de Docker
  • TTL automático: la entrada en Redis expira al mismo tiempo que el token JWT original
  • Verificación: el guard de JWT consulta Redis en cada request autenticado

3.4 Rate limiting en login

El endpoint de autenticación tiene un límite estricto de intentos para mitigar ataques de fuerza bruta y relleno de credenciales (credential stuffing).

  • Máximo 3 intentos por minuto por dirección IP
  • Al superar el límite: respuesta 429 Too Many Requests

4. Protección de Credenciales y Secretos

4.1 Docker Secrets

Todos los secretos del sistema (contraseñas, claves criptográficas, tokens de servicio) se gestionan mediante el mecanismo de Docker Secrets. Los valores se almacenan en archivos independientes fuera del proceso de la aplicación y se montan en el sistema de archivos del contenedor como archivos de solo lectura en /run/secrets/.

Este enfoque garantiza que los secretos nunca aparezcan en variables de entorno visibles (docker inspect), en logs del sistema, ni en el repositorio de código.

SecretoUsoFortaleza
jwt_secret Firma de tokens JWT 64 bytes hexadecimales (512 bits)
postgres_password Acceso a la base de datos 48 bytes hexadecimales (384 bits)
ldap_bind_credentials Cuenta de servicio AD para búsquedas LDAP Contraseña compleja rotada periódicamente
bridge_secret Autenticación del AD Bridge interno 48 bytes hexadecimales (384 bits)
mail_bridge_secret Autenticación del puente de correo externo 48 bytes hexadecimales (384 bits)
smtp_pass Cuenta de correo saliente (SMTP) Token de aplicación de 16 caracteres

4.2 Exclusión del repositorio Git

El directorio secrets/ contiene un archivo .gitignore que excluye todos los archivos *.txt, impidiendo que cualquier credencial sea comprometida accidentalmente en el historial del repositorio.

4.3 Generación criptográfica de secretos

Todos los secretos fueron generados utilizando crypto.randomBytes() de Node.js (CSPRNG — generador de números pseudoaleatorios criptográficamente seguro). Ningún secreto fue elegido manualmente ni reutilizado entre entornos.

5. Seguridad en la Capa de Transporte (TLS/HTTPS)

5.1 Acceso público — nginx con TLS

El acceso externo a la plataforma se realiza exclusivamente a través de HTTPS. nginx actúa como proxy inverso y termina la conexión TLS antes de reenviar el tráfico a los servicios internos.

  • Puerto 443 (HTTPS) expuesto al exterior
  • Certificado TLS distribuido a los equipos del dominio mediante Política de Grupo (GPO) del controlador de dominio Windows Server
  • Puerto 80 (HTTP) no expuesto al exterior
  • Backend y frontend accesibles solo desde localhost en el servidor

5.2 Comunicación interna — puente de correo (mail-bridge)

El puente de correo (mail-bridge) opera en una PC con Windows en la red 172.21.36.104, separada del servidor principal por un firewall FortiGate. La comunicación entre ambos componentes utiliza TLS con certificado autofirmado.

  • Certificado autofirmado con SAN (Subject Alternative Name) para la IP 172.21.36.104
  • Algoritmo: RSA 2048 bits, validez 10 años
  • El servidor HTTPS del bridge escucha en el puerto 3002
  • El backend verifica la identidad del bridge mediante secreto compartido adicional

5.3 Comunicación con servicios de correo

La comunicación con el servidor de correo institucional (10.201.2.37) utiliza los protocolos seguros estándar:

  • IMAP sobre TLS (puerto 993) para recepción
  • SMTP con STARTTLS (puerto 587) para envío

6. Controles de Acceso y Autorización

6.1 Control de acceso basado en roles (RBAC)

Los permisos de acceso a módulos y funcionalidades están determinados por los grupos del Active Directory a los que pertenece cada usuario. Los roles se extraen del atributo memberOf en el momento del login y se incluyen en el payload del token JWT.

  • Roles institucionales: DIREDTOS, TICOM, AYUDANTIADIREDTOS, AYUDANTIARECTORADO, entre otros
  • Rol admin: acceso al panel de administración de usuarios y configuración
  • Cada endpoint de la API declara explícitamente qué roles tienen acceso

6.2 Guard global de autenticación

Todos los endpoints de la API requieren autenticación JWT por defecto. Las rutas públicas (login, health check) se declaran explícitamente con un decorador @Public(), evitando exposición accidental de endpoints protegidos.

6.3 Permisos configurables por grupo

Los administradores pueden restringir el acceso a módulos específicos (chat, incidencias, reservas, correo, redactar-MTO) por grupo de Active Directory, sin necesidad de modificar el código fuente. Los grupos sin configuración explícita mantienen acceso total para garantizar compatibilidad con versiones anteriores.

6.4 Creación de usuarios — orden de operaciones

El proceso de alta de usuarios implementa un orden de operaciones con rollback automático para garantizar consistencia entre sistemas:

  • 1. Creación en Google Workspace (si falla, se detiene el proceso)
  • 2. Creación en Active Directory con cambio de contraseña forzado en primer login
  • 3. Si AD falla → rollback automático en Google Workspace
  • 4. Registro del usuario en la base de datos local
  • 5. Envío de email de bienvenida (no bloqueante)

7. Protección de APIs y Endpoints

7.1 Validación estricta de entradas

Todos los endpoints de la API aplican validación estricta sobre los datos de entrada mediante el pipe global de validación de NestJS con las siguientes configuraciones:

  • whitelist: true — propiedades no declaradas en el DTO son eliminadas automáticamente
  • forbidNonWhitelisted: true — requests con propiedades no esperadas son rechazados
  • transform: true — los tipos de datos son convertidos y validados automáticamente

7.2 Cabeceras de seguridad HTTP (Helmet)

El middleware Helmet se aplica globalmente a todas las respuestas de la API, configurando automáticamente las siguientes cabeceras de seguridad:

  • X-Content-Type-Options: nosniff — previene MIME-type sniffing
  • X-Frame-Options: SAMEORIGIN — protección contra clickjacking
  • X-XSS-Protection — filtro XSS en navegadores legacy
  • Strict-Transport-Security — fuerza HTTPS en navegadores modernos
  • Content-Security-Policy — restricción de orígenes de recursos

7.3 Protección CORS

La política de Cross-Origin Resource Sharing (CORS) restringe qué orígenes pueden realizar peticiones a la API. Solo el frontend institucional y el servidor de desarrollo están en la lista de orígenes permitidos.

7.4 Endpoint de ingestión del bridge — doble protección

El endpoint POST /api/mail/bridge/ingest (recepción de correos desde el bridge externo) implementa dos capas de protección independientes:

  • Whitelist de IP: solo se aceptan conexiones desde la dirección IP del bridge (172.21.36.104). Cualquier otra IP recibe 403 Forbidden sin revelar información adicional.
  • Secreto compartido: el bearer token se verifica usando crypto.timingSafeEqual(), que previene ataques de temporización (timing attacks) que podrían deducir el secreto midiendo el tiempo de respuesta.

8. Auditoría y Trazabilidad

8.1 Log de autenticación

Cada intento de autenticación (exitoso o fallido) genera una entrada de log estructurada que incluye:

  • Tipo de evento: AUTH_OK o AUTH_FAIL
  • Nombre de usuario utilizado en el intento
  • Dirección IP de origen
  • Timestamp (UTC)

Los intentos fallidos son especialmente relevantes para la detección de ataques de fuerza bruta o uso de credenciales comprometidas.

8.2 Audit log de acciones administrativas

Todas las acciones realizadas desde el panel de administración quedan registradas en la tabla admin_audit_log de la base de datos, con:

  • ID y nombre del usuario que realizó la acción
  • Descripción de la acción (ej: "Creó usuario X en AD", "Actualizó contraseña de correo DIREDTOS")
  • Timestamp de la operación

8.3 Filtro global de excepciones

Un filtro global intercepta todos los errores no controlados de la API y devuelve respuestas de error estructuradas sin exponer stack traces, rutas internas, ni información sensible del servidor al cliente.

9. Seguridad de Infraestructura y Contenedores

9.1 Exposición de puertos

En el entorno de producción, los servicios internos no están expuestos directamente a la red. Solo nginx (proxy inverso) tiene puertos externos accesibles.

9.2 Aislamiento de red entre contenedores

Todos los contenedores operan en una red Docker interna privada (192.168.200.0/24). La comunicación entre servicios utiliza nombres de servicio DNS internos (postgres, redis, openldap, etc.), sin exposición a la red del host.

9.3 Healthchecks y reinicio automático

Los servicios críticos (PostgreSQL, Redis) tienen configurados healthchecks que verifican disponibilidad antes de iniciar servicios dependientes. Todos los contenedores están configurados con política restart: unless-stopped para recuperación automática ante fallos.

9.4 Gestión de cuentas inactivas (cron automático)

Un proceso cron ejecutado diariamente a las 2:00 AM aplica la política de inactividad de cuentas del AD:

  • Inactividad mayor a 7 meses → deshabilita la cuenta en AD
  • Inactividad mayor a 8 meses y ya deshabilitada → elimina la cuenta de AD
  • Basado en el atributo lastLogonTimestamp del Active Directory
  • Cuentas de servicio y administrativas excluidas del proceso automático

10. Protección del Frontend

10.1 Sin tokens en almacenamiento local

El frontend Angular no almacena tokens de sesión en localStorage ni en sessionStorage. El token JWT reside exclusivamente en la cookie httpOnly gestionada por el navegador, eliminando el vector de ataque XSS más común.

10.2 Interceptor de credenciales

Todas las peticiones HTTP del frontend incluyen automáticamente las cookies de sesión mediante el flag withCredentials: true. Esto garantiza que el token se envíe de forma transparente sin ser accesible desde el código de la aplicación.

10.3 Manejo de errores de autenticación

Un interceptor global detecta respuestas 401 Unauthorized del servidor y limpia la sesión local del usuario, redirigiendo al login. Esto previene estados inconsistentes donde el frontend cree que hay sesión activa cuando el servidor ya la invalidó.

10.4 Límites de tamaño en uploads

Los endpoints de carga de archivos tienen límites estrictos por tipo para prevenir ataques de denegación de servicio por archivos masivos:

  • Avatares de usuario: 6 MB
  • Adjuntos de chat: 50 MB (JPG, PNG, GIF, WebP, PDF, DOCX, XLS)
  • Adjuntos de incidencias: 10 MB (solo imágenes)
  • Adjuntos de borradores MTO: 5 MB por archivo (20 MB en backend)

11. Pendientes y Recomendaciones

Los siguientes puntos son mejoras planificadas que no afectan la seguridad operativa actual, pero se recomienda implementar en los próximos ciclos de mantenimiento.
ÍtemDescripciónPrioridad
Rotación de contraseña PostgreSQL Actualizar la contraseña de la base de datos y el archivo de secreto correspondiente. Requiere ALTER USER en PostgreSQL y rebuild del contenedor. MEDIA
Rotación de contraseña cuenta de servicio AD Rotar la contraseña de la cuenta svc-pac utilizada para operaciones en Active Directory. Requiere actualizar el secreto ldap_bind_credentials. MEDIA
Certificado TLS público (CA reconocida) Reemplazar el certificado autofirmado del servidor por un certificado emitido por una autoridad certificante reconocida (Let's Encrypt u otra), eliminando la necesidad de distribuirlo por GPO. BAJA
Renovación periódica del certificado del bridge El certificado autofirmado del mail-bridge tiene validez de 10 años. Se recomienda establecer un procedimiento de renovación documentado. BAJA
Autenticación multifactor (MFA) Implementar segundo factor de autenticación para cuentas con roles administrativos (admin, TICOM). MEDIA
