Descripción del sistema

La plataforma Intranet Diredtos es un sistema web de uso interno desarrollado para la Dirección de Educación e Institutos. Integra los siguientes módulos funcionales:

  • Chat institucional con mensajería en tiempo real y envío de archivos adjuntos
  • Gestión de incidencias con seguimiento de estado y asignación
  • Sistema de reservas de espacios y equipamiento para videoconferencias
  • Módulo de correo con integración IMAP/SMTP al servidor de correo institucional
  • Redacción MTO (Draft-Mail) con flujo de aprobación y firma digital
  • Panel de administración con gestión de usuarios en Active Directory y Google Workspace
  • Notificaciones push y presencia en tiempo real (Socket.IO)

Autenticación y gestión de sesiones

3.1 Autenticación contra Active Directory

Todos los usuarios del sistema se autentican exclusivamente contra el Active Directory local mediante el protocolo LDAP. No existen contraseñas locales almacenadas en la base de datos del sistema. El servidor AD reside en la red interna y no es accesible desde internet.

  • Protocolo: LDAP sobre red interna (dominio iugnad.lan, controlador 10.98.40.22)
  • Credenciales de cuenta de servicio: almacenadas como Docker Secret, nunca en variables de entorno planas
  • Error AD 773 (contraseña expirada): devuelve mensaje claro al usuario en lugar de error genérico
  • Roles y permisos: extraídos del atributo memberOf del AD en cada login

3.2 Tokens JWT con cookie httpOnly

Tras una autenticación exitosa, el servidor emite un token JWT entregado al navegador exclusivamente mediante una cookie httpOnly. Esta modalidad impide que cualquier script JavaScript pueda leer o robar el token de sesión.

  • httpOnly: true — inaccesible desde JavaScript
  • SameSite: Strict — protección contra ataques CSRF
  • Secure: true en producción — solo transmitida por HTTPS
  • Vigencia del token: 8 horas
  • El payload incluye un identificador único de token (jti) generado criptográficamente
Mejora respecto a la versión anterior: En versiones previas el token JWT se almacenaba en localStorage del navegador, siendo accesible desde JavaScript. Esta vulnerabilidad fue corregida migrando a cookie httpOnly, eliminando el riesgo de robo de sesión por XSS.

3.3 Lista negra de tokens (Redis)

Al cerrar sesión, el identificador único del token (jti) se registra en Redis como token invalidado. Cualquier intento posterior de usar ese token es rechazado, incluso si el token aún no expiró.

  • Almacenamiento: Redis 7 en memoria, accesible solo desde la red interna de Docker
  • TTL automático: la entrada en Redis expira al mismo tiempo que el token JWT original
  • Verificación: el guard de JWT consulta Redis en cada request autenticado

3.4 Rate limiting en login

El endpoint de autenticación tiene un límite estricto de intentos para mitigar ataques de fuerza bruta y relleno de credenciales.

  • Máximo 3 intentos por minuto por dirección IP
  • Al superar el límite: respuesta 429 Too Many Requests

Protección de credenciales y secretos

4.1 Docker Secrets

Todos los secretos del sistema se gestionan mediante Docker Secrets. Los valores se almacenan en archivos independientes montados en el contenedor como archivos de solo lectura en /run/secrets/. Los secretos nunca aparecen en variables de entorno visibles, en logs, ni en el repositorio de código.

Secreto Uso Fortaleza
jwt_secretFirma de tokens JWT64 bytes hexadecimales (512 bits)
postgres_passwordAcceso a la base de datos48 bytes hexadecimales (384 bits)
ldap_bind_credentialsCuenta de servicio AD para búsquedas LDAPContraseña compleja rotada periódicamente
bridge_secretAutenticación del AD Bridge interno48 bytes hexadecimales (384 bits)
mail_bridge_secretAutenticación del puente de correo externo48 bytes hexadecimales (384 bits)
smtp_passCuenta de correo saliente (SMTP)Token de aplicación de 16 caracteres

4.2 Exclusión del repositorio Git

El directorio secrets/ contiene un archivo .gitignore que excluye todos los archivos *.txt, impidiendo que cualquier credencial sea comprometida accidentalmente en el historial del repositorio.

4.3 Generación criptográfica de secretos

Todos los secretos fueron generados utilizando crypto.randomBytes() de Node.js (CSPRNG). Ningún secreto fue elegido manualmente ni reutilizado entre entornos.

Seguridad en la capa de transporte (TLS/HTTPS)

5.1 Acceso externo — nginx con TLS

El acceso a la plataforma se realiza exclusivamente a través de HTTPS. nginx actúa como proxy inverso y termina la conexión TLS antes de reenviar el tráfico a los servicios internos.

  • Puerto 443 (HTTPS) expuesto hacia la red institucional
  • Certificado TLS distribuido a los equipos del dominio mediante Política de Grupo (GPO) del controlador de dominio Windows Server
  • Puerto 80 (HTTP) no expuesto al exterior
  • Backend y frontend accesibles solo desde localhost en el servidor

5.2 Comunicación interna — puente de correo (mail-bridge)

El puente de correo opera en una PC Windows en la red 172.21.36.104 (TELEMÁTICO), separada del servidor principal por un firewall FortiGate. La comunicación entre ambos componentes utiliza TLS con certificado autofirmado.

  • Certificado autofirmado con SAN (Subject Alternative Name) para la IP 172.21.36.104
  • Algoritmo: RSA 2048 bits, validez 10 años
  • El servidor HTTPS del bridge escucha en el puerto 3002
  • El backend verifica la identidad del bridge mediante secreto compartido adicional

5.3 Comunicación con servicios de correo

  • IMAP sobre TLS (puerto 993) para recepción
  • SMTP con STARTTLS (puerto 587) para envío

Controles de acceso y autorización

6.1 Control de acceso basado en roles (RBAC)

Los permisos de acceso están determinados por los grupos del Active Directory a los que pertenece cada usuario. Los roles se extraen del atributo memberOf en el momento del login y se incluyen en el payload del token JWT.

  • Roles institucionales: DIREDTOS, TICOM, AYUDANTIADIREDTOS, AYUDANTIARECTORADO, entre otros
  • Rol admin: acceso al panel de administración de usuarios y configuración
  • Cada endpoint de la API declara explícitamente qué roles tienen acceso

6.2 Guard global de autenticación

Todos los endpoints de la API requieren autenticación JWT por defecto. Las rutas públicas se declaran explícitamente con el decorador @Public(), evitando la exposición accidental de endpoints protegidos.

6.3 Permisos configurables por grupo

Los administradores pueden restringir el acceso a módulos específicos (chat, incidencias, reservas, correo, redactar-MTO) por grupo de Active Directory, sin necesidad de modificar el código fuente. Los grupos sin configuración explícita mantienen acceso total para garantizar compatibilidad con versiones anteriores.

6.4 Creación de usuarios — orden de operaciones con rollback

  1. Creación en Google Workspace (si falla, se detiene el proceso)
  2. Creación en Active Directory con cambio de contraseña forzado en primer login
  3. Si AD falla → rollback automático en Google Workspace
  4. Registro del usuario en la base de datos local
  5. Envío de email de bienvenida (no bloqueante)

Protección de APIs y endpoints

7.1 Validación estricta de entradas

  • whitelist: true — propiedades no declaradas en el DTO son eliminadas automáticamente
  • forbidNonWhitelisted: true — requests con propiedades no esperadas son rechazados
  • transform: true — los tipos de datos son convertidos y validados automáticamente

7.2 Cabeceras de seguridad HTTP (Helmet)

  • X-Content-Type-Options: nosniff — previene MIME-type sniffing
  • X-Frame-Options: SAMEORIGIN — protección contra clickjacking
  • X-XSS-Protection — filtro XSS en navegadores legacy
  • Strict-Transport-Security — fuerza HTTPS en navegadores modernos
  • Content-Security-Policy — restricción de orígenes de recursos

7.3 Protección CORS

La política CORS restringe qué orígenes pueden realizar peticiones a la API. Solo el frontend de la Intranet y el servidor de desarrollo figuran en la lista de orígenes permitidos.

7.4 Endpoint de ingestión del bridge — doble protección

El endpoint POST /api/mail/bridge/ingest implementa dos capas de protección independientes:

  • Whitelist de IP: solo se aceptan conexiones desde 172.21.36.104. Cualquier otra IP recibe 403 Forbidden sin información adicional.
  • Secreto compartido: el bearer token se verifica usando crypto.timingSafeEqual(), que previene ataques de temporización.

Auditoría y trazabilidad

8.1 Log de autenticación

Cada intento de autenticación (exitoso o fallido) genera una entrada de log estructurada que incluye:

  • Tipo de evento: AUTH_OK o AUTH_FAIL
  • Nombre de usuario utilizado en el intento
  • Dirección IP de origen
  • Timestamp (UTC)

8.2 Audit log de acciones administrativas

Todas las acciones realizadas desde el panel de administración quedan registradas en la tabla admin_audit_log de la base de datos, con:

  • ID y nombre del usuario que realizó la acción
  • Descripción de la acción (ej: "Creó usuario X en AD", "Actualizó contraseña de correo DIREDTOS")
  • Timestamp de la operación

8.3 Filtro global de excepciones

Un filtro global intercepta todos los errores no controlados de la API y devuelve respuestas de error estructuradas sin exponer stack traces, rutas internas ni información sensible del servidor al cliente.

9.2 Aislamiento de red entre contenedores

Todos los contenedores operan en una red Docker interna privada (192.168.200.0/24). La comunicación entre servicios utiliza nombres DNS internos (postgres, redis, etc.), sin exposición a la red del host.

9.3 Healthchecks y reinicio automático

Los servicios críticos (PostgreSQL, Redis) tienen configurados healthchecks que verifican disponibilidad antes de iniciar servicios dependientes. Todos los contenedores están configurados con política restart: unless-stopped para recuperación automática ante fallos.

9.4 Gestión de cuentas inactivas (cron automático)

Un proceso cron ejecutado diariamente a las 2:00 AM aplica la política de inactividad:

  • Inactividad mayor a 7 meses — deshabilita la cuenta en AD
  • Inactividad mayor a 8 meses y ya deshabilitada — elimina la cuenta de AD
  • Basado en el atributo lastLogonTimestamp del Active Directory
  • Cuentas de servicio y administrativas excluidas del proceso automático
10

Protección del frontend

10.1 Sin tokens en almacenamiento local

El frontend Angular no almacena tokens de sesión en localStorage ni en sessionStorage. El token JWT reside exclusivamente en la cookie httpOnly gestionada por el navegador, eliminando el vector de ataque XSS más común.

10.2 Interceptor de credenciales

Todas las peticiones HTTP del frontend incluyen automáticamente las cookies de sesión mediante el flag withCredentials: true. El token se envía de forma transparente sin ser accesible desde el código de la aplicación.

10.3 Manejo de errores de autenticación

Un interceptor global detecta respuestas 401 Unauthorized, limpia la sesión local y redirige al login, previniendo estados inconsistentes donde el frontend cree tener sesión activa cuando el servidor ya la invalidó.

10.4 Límites de tamaño en uploads

  • Avatares de usuario: 6 MB
  • Adjuntos de chat: 50 MB (JPG, PNG, GIF, WebP, PDF, DOCX, XLS)
  • Adjuntos de incidencias: 10 MB (solo imágenes)
  • Adjuntos de borradores MTO: 5 MB por archivo (20 MB en validación backend)

Backups

Los procedimientos de backup se ejecutan fuera del sistema de la aplicación, mediante scripts bash y tareas programadas (cron) directamente en los servidores. Cada servidor VM realiza su propio backup y lo copia vía red al servidor NAS central.

11.1 Base de Datos (PostgreSQL)

La herramienta utilizada es pg_dump, ejecutada desde cada servidor VM mediante cron. El backup se genera en formato comprimido custom (-F c) y se copia al servidor NAS mediante montaje de red.

Servidores y bases de datos respaldadas:

  • Servidor SIU — base de datos: gestion (puerto 5432) → /media/nas/repo-docentes/db/
  • Servidor Intranet — base de datos: intranet (puerto 5442) → /media/nas/intranet/db/
  • Servidor GLPI/Ticket — base de datos: ticket (MySQL, mysqldump) → /media/nas/glpi/
ParámetroDetalle
Herramientapg_dump (PostgreSQL) / mysqldump (MySQL/GLPI)
FormatoCustom comprimido (-F c) para PostgreSQL / SQL + gzip para MySQL
FrecuenciaDiaria (cron, horario configurable por servidor)
Destino NAS/var/backups/todo/siu/db/, /var/backups/todo/intranet/db/, /var/backups/todo/proxmox/

11.5 Procedimiento de Restauración

Restauración de base de datos PostgreSQL:

  1. Localizar el backup a restaurar en el NAS: ls -lh /var/backups/todo/siu/db/
  2. Copiar el backup al servidor destino: cp /var/backups/todo/siu/db/gestion_YYYYMMDDHHMM.backup /root/restore/
  3. Restaurar con pg_restore: pg_restore -h localhost -p 5432 -U postgres -d gestion -v gestion_YYYYMMDDHHMM.backup

Restauración de VMs Proxmox:

  1. Acceder a la interfaz web de Proxmox
  2. Ir a la VM → Backup → seleccionar backup (.vma.zst) → Restore
  3. O vía CLI: qmrestore /var/backups/todo/proxmox/{ip}/dump/vzdump-qemu-{vmid}-{fecha}.vma.zst {vmid}

Restauración de archivos adjuntos Docker:

rsync -avz /var/backups/todo/intranet/adjuntos/ \
  /var/lib/docker/volumes/intranet2026_mail_attachments/_data/
