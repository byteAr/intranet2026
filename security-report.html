1. Resumen ejecutivo

Se implementaron 7 mejoras de seguridad sobre la plataforma intranet institucional. Las medidas cubren autenticación, gestión de tokens, secretos de infraestructura, control de acceso a endpoints y trazabilidad de eventos de autenticación.

Se generaron nuevas claves criptográficas para reemplazar los valores placeholder que existían en producción.

5. Descripción técnica de cada mejora

5.1 JWT en cookie httpOnly

El token JWT ya no se almacena en localStorage del navegador. En el login, el backend emite una cookie con los flags:

  • httpOnly: JavaScript del cliente no puede leer la cookie (protección XSS)
  • Secure: Solo se envía por HTTPS en producción
  • SameSite=Strict: Solo se envía en solicitudes del mismo origen (protección CSRF)
  • Expiración: 8 horas (igual que antes)

El frontend ya no guarda el token; envía withCredentials: true y el navegador adjunta la cookie automáticamente.

5.2 Blacklist de tokens en Redis

El payload del JWT ahora incluye un campo jti (JWT ID) único por token. Al hacer logout:

  • El backend extrae el jti y el tiempo de expiración (exp) del token
  • Almacena la clave bl:{jti} en Redis con TTL igual al tiempo restante del token
  • En cada petición autenticada, el guard verifica que el jti no esté en la blacklist

Redis 7 se agrega como servicio Docker. El servicio backend depende de Redis (healthcheck). Si Redis no está disponible, la blacklist falla abierta (logs el error, no bloquea el sistema).

5.3 Docker Secrets

Las claves JWT_SECRET, BRIDGE_SECRET y MAIL_BRIDGE_SECRET se leen desde archivos montados en /run/secrets/ en lugar de variables de entorno. Ventajas:

  • No aparecen en docker inspect ni en logs del proceso
  • No se replican a todos los workers (en Docker Swarm)
  • Los archivos *.txt están en .gitignore — nunca se comiten al repo

5.4 IP Whitelist en BridgeSecretGuard

El endpoint POST /api/mail/bridge/ingest (público con secret) ahora rechaza peticiones que no provengan de 172.21.36.104 (PC del mail bridge). La verificación ocurre antes de la comparación del secreto.

5.5 Rate limiting

El endpoint POST /api/auth/login se redujo de 5 a 3 intentos por minuto. Los demás endpoints de autenticación mantienen sus límites.

5.6 Audit log de autenticación

El guard LdapAuthGuard ahora registra en el logger de NestJS:

  • [AUTH_OK] user={username} ip={ip} — login exitoso
  • [AUTH_FAIL] user={username} ip={ip} reason=invalid_credentials — credenciales incorrectas
  • [AUTH_FAIL] user={username} ip={ip} reason=password_change_required — error AD 773

Los logs son visibles con: docker compose logs backend | grep AUTH_
